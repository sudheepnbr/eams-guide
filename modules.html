Module reference

Complete product-area guide for operators and implementers. Activation is controlled in Admin Settings (MODULE_ACTIVATION_JSON).

1. Asset

Path: /module/assets · Key: asset · Access: MODULE_ACCESS_ASSET

  • Asset register with KPI strip (total, assigned, unassigned, scrapped, warranty due, under service).
  • GRN (goods receipt), register wizard, transfer, bulk barcode, import/export, consumables, warehouse stock, software register.
  • Masters: category, sub-category, floor, location, vendor, warehouse, employees — scoped by instance.
  • Software access reviews and related compliance tooling.

List data is paged via /module/assets/api/table-page; vendor catalog sync runs on vendor master maintenance, not every dashboard open.

2. Maintenance

Path: /module/asset-maintenance · Key: maintenance · Access: MODULE_ACCESS_MAINTENANCE

  • Work orders and preventive maintenance against assets.
  • KPIs for open, overdue, under maintenance, completed, critical, and Service Desk transfers.
  • Technicians, SLA / expected completion, before/after photos and invoices.

3. Service Desk

Path: /module/service-desk (portal for requesters) · Key: service_desk

  • Tickets: Incident, Request, Problem, Change categories.
  • Technician dashboard with KPI filters, dynamic search, instance and assignee scope.
  • Requester portal for “my tickets”; inbound email processing when configured.
  • Asset picker linkage, timeline, email compose, milestone UI.

4. Change

Path: /module/changes · Key: change · Access: MODULE_ACCESS_CHANGE

  • RFC-style change records with approval workflow and risk/priority.
  • KPI strip: total, open, pending approval, on hold, approved, rejected, completed, high/critical risk.
  • Approver configuration for admins; exportable change list.

5. Quotation and PO

Path: /module/quotations · Key: quotation · Access: MODULE_ACCESS_QUOTATION

  • Quotations, RFQ, and purchase-order style approvals.
  • Vendor master shared with Assets; mail workflows for vendors when SMTP is configured.
  • KPI filters: total, pending, under review, approved, rejected, on hold, overdue, high value.

6. Projects

Path: /module/projects · Key: project · Access: MODULE_ACCESS_PROJECT

  • Projects, tasks, templates, risks and issues.
  • KPI view: onboarded, on track, need attention, at risk, completed, total budget.
  • Schema bootstrapped by SQL scripts + ensure_* on first open (same pattern as DMS).

7. Floor Map

Path: /module/floor-map · Key: floor_map · Access: MODULE_ACCESS_FLOOR_MAP

  • Visual floor plans with asset pins.
  • View vs manage capabilities assigned per role in the Role Access Matrix.

8. Document Management (DMS)

Path: /module/documents · Key: dms (default off) · Access: MODULE_ACCESS_DMS

  • Controlled documents: register, quarantine upload, revision, review, approve, publish.
  • Scoped DMS roles (READER, AUTHOR, REVIEWER, APPROVER, DOCUMENT_CONTROLLER, …) expand through dms.RolePermission.
  • Owner ≠ reading audience; published download requires audience or oversight permission.
  • Library and register KPI cards; tasks list for pending workflow work.

Operator checklist

  1. Admin Settings → turn on Document Management.
  2. Open Documents once (or run db/sql/048_dms_module.sql) so tables/permissions exist.
  3. Assign scoped DMS roles — portal roles alone do not grant approve/publish.
  4. Grant MODULE_ACCESS_DMS only when a role should see the menu without a DMS assignment.

Longer assessment notes are in the repo: docs/dms-assessment-and-plan.md.

9. E-Learning

Path: /module/e-learning · Key: elearning · Access: MODULE_ACCESS_ELEARNING

  • Course Library, Request a course, My requests, My Task, My Courses, Create course, Certificates, Course Calendar, Target Audience.
  • Main KPI chrome: Assigned, In progress, Due this week, Overdue, Mandatory, Published.
  • SCORM / course package build from materials (including large video uploads), quiz attempts, continue-gates between sections.
  • Certificates with QR verification pages (hosted certificate verify flow).
  • Enrollment, re-enrollment after quiz fail / expiry, launch-date rules for COO publish.

Workflow summary (course request → publish)

  1. Requester submits a course request with format, materials, and audience details.
  2. HR / preparation / quality stages review and forward (stage labels appear on My Task).
  3. Preparation team builds or uploads the SCORM package; competency checklist when required.
  4. Course owner / EL Admin prepares, then leadership (including COO) publishes with launch-date checks.
  5. Learners take the course from the library; completion issues a certificate and optional QR verify page.

Detailed internal workflow write-up: docs/EAMS_ELearning_Full_Workflows.docx (repo).

Admin, Users, FAQs

  • Admin Settings — /admin: organization masters, identity, Role Access Matrix, module activation, feature flags, notification templates, certificate signatories, purge tools.
  • Users — /module/users when permitted.
  • FAQs — /module/faqs for privileged helpers.
  • Dashboard — /dashboard with module tiles and counts.

Selected JSON APIs

Prefix /api/v1 (OpenAPI: /docs when enabled).

  • Assets — GET/POST /assets, GET/PUT /assets/{id}
  • Service Desk — /service-desk/tickets
  • Changes — /changes
  • Quotations — submit / decision / pending
  • Auth — GET /auth/me
  • Admin — users, departments, roles, services, access

Module UIs also call many /module/…/api/… endpoints for tables, KPIs, and wizards.
